# Stage D - Python and .NET runtime bridges

## Status

Forward-compatible design baseline. Managed runtime hosting is planned for D4,
after the native D1 vertical slice and ABI stabilization work. Decisions in D0
must not make D4 require changes to command IDs, driver contracts, schemas,
execution policy, or ARTestStudio integration.

## Decision

ARTestEngine will not load CPython or CLR directly into its process. Python and
.NET extensions run behind dedicated local runtime-host processes:

```text
ARTestEngine
    |
ProcessRuntimeAdapter
    |
Versioned local protocol
    +----------------------+----------------------+
    |                                             |
ARTestPythonHost.exe                       ARTestDotNetHost.exe
    |                                             |
Python SDK/package                          .NET SDK/assembly
```

This preserves a stable engine process while allowing language runtimes and
dependencies to evolve independently.

## Why process isolation is required

### Python

Embedding Python would introduce global interpreter state, the GIL, native
wheel compatibility, interpreter-version constraints, module-global state, and
unreliable unloading of native extension modules. A Python package failure could
also terminate or corrupt ARTestEngine.

### .NET

Embedding CLR would introduce runtime selection, assembly resolution, native
dependency conflicts, `AssemblyLoadContext` limitations, background tasks, and
unload behavior that is difficult to guarantee when references or threads
remain. A fatal managed/native interop failure could affect the engine process.

### Common benefit

Process isolation provides:

- explicit startup and shutdown;
- runtime and dependency isolation per package or trust group;
- crash detection;
- bounded cleanup grace periods;
- forced termination as a last-resort containment mechanism;
- CPU, memory, and permission restrictions in later hardening;
- independent Python/.NET SDK release cadence.

## Canonical protocol model

The process protocol mirrors the logical native ABI rather than exposing C
memory layouts. It uses the same:

- extension and component IDs;
- component kinds;
- contract and operation IDs;
- manifests and schemas;
- payload envelopes;
- status categories;
- invocation IDs;
- deadlines and cancellation;
- diagnostics, logs, and results;
- lifecycle sequence.

ARTestEngine maps native and managed endpoints into one internal
`ExtensionEndpoint` abstraction. Parser, compiler, executor, catalog consumers,
and ARTestStudio cannot determine an extension language from the invocation API
and do not branch on Python versus .NET.

## Transport baseline

The intended local transport is Windows named pipes with length-prefixed,
versioned Protocol Buffer messages. The transport is local-only by default.
Protocol Buffers are selected because official implementations exist for C++,
Python, and .NET and because unknown fields allow controlled protocol evolution.

The initial protocol requires messages equivalent to:

```text
Hello / HelloAck
DescribeExtension / ExtensionDescriptor
CreateComponent / CreateComponentResult
Invoke / InvocationResult
CancelInvocation / CancelAck
ShutdownComponent / ShutdownResult
DestroyComponent
ShutdownExtension / ShutdownExtensionResult
LogEvent
Heartbeat
```

The exact `.proto` schema is deferred until D4. D0 fixes semantic requirements,
not generated message field numbers.

## Process and session identity

Every runtime-host launch receives:

- protocol major/minor range;
- a cryptographically random session token;
- a unique named-pipe endpoint;
- package root and manifest path;
- extension ID expected by the engine;
- logging and startup timeout configuration.

The first message authenticates the local session token and negotiates protocol
versions. ARTestEngine rejects an endpoint whose extension identity does not
match the validated manifest.

Opaque native pointers never cross the process boundary. Extension, component,
service, and invocation handles are scoped 64-bit tokens generated by the side
that owns them. Tokens are invalidated on disconnect or endpoint restart.

## Invocation flow

```text
Engine assigns invocation ID and deadline
-> sends operation and request payload
-> endpoint invokes language SDK component
-> endpoint streams logs/events tagged with invocation ID
-> endpoint returns one terminal status and optional result payload
-> Engine records the canonical StepResult/diagnostic
```

Cancellation sends `CancelInvocation`. The language SDK exposes a cooperative
token:

- Python: an `asyncio.Event`-compatible cancellation object plus deadline;
- .NET: a linked `CancellationToken` plus deadline.

If the endpoint ignores cancellation, ARTestEngine waits for the configured
grace period, records a timeout, attempts endpoint shutdown, and may terminate
the runtime-host process. A terminated endpoint invalidates all of its component
instances and forces driver recovery or run failure.

## Python developer model

The future `artest-sdk` Python package should expose decorators or explicit
registration without requiring developers to understand the wire protocol:

```python
from artest_sdk import command, CommandContext, Result

@command(
    type_id="com.example.command.measure-voltage",
    contract="artest.contract.command.v1",
    parameters="schemas/measure-voltage.parameters.json",
)
async def measure_voltage(context: CommandContext, parameters: dict) -> Result:
    supply = await context.resolve_service(
        "artest.contract.instrument.power-supply.v1",
        parameters["instrument"],
    )
    return await supply.invoke("measure-voltage", parameters)
```

Discovery should use an explicit manifest entry point. Importing arbitrary
modules recursively is not allowed. Each package uses a controlled virtual
environment or locked dependency environment selected by its manifest.

The Python host converts unhandled exceptions into
`ARTEST_STATUS_EXTENSION_FAILURE`, publishes a sanitized traceback to logs, and
never sends a Python object representation as a public result.

## .NET developer model

The future `ARTest.SDK` NuGet package should expose interfaces and source
generators/attributes that map to the same canonical descriptors:

```csharp
[ARTestCommand(
    TypeId = "com.example.command.measure-voltage",
    Contract = "artest.contract.command.v1")]
public sealed class MeasureVoltageCommand : IARTestCommand
{
    public async ValueTask<ARTestResult> ExecuteAsync(
        ARTestCommandContext context,
        JsonElement parameters,
        CancellationToken cancellationToken)
    {
        // Resolve and invoke a driver capability through the SDK.
        throw new NotImplementedException();
    }
}
```

`ARTestDotNetHost` loads only the manifest-declared assembly and type/entry
point. `AssemblyLoadContext` may be used for dependency organization, but
process termination remains the reliable isolation and unload boundary.

Unhandled exceptions are converted to the canonical extension-failure status.
The host records a sanitized exception type, message, and stack trace without
serializing arbitrary managed objects.

## Instrument Drivers in managed languages

Managed Instrument Drivers implement the same lifecycle and capability
contracts as native drivers. The engine does not distinguish a Python driver
from a native driver when resolving a power-supply capability.

Managed drivers must still provide:

- bounded I/O timeout behavior;
- cooperative cancellation;
- explicit initialization and shutdown;
- serialized access unless concurrency is declared and supported;
- deterministic result schemas;
- cleanup after partial initialization;
- no direct console or ARTestStudio dependency.

Drivers requiring vendor C SDKs may use Python native wheels or .NET P/Invoke
inside their isolated runtime process. A vendor crash then affects the runtime
host rather than ARTestEngine.

## Tool components

Future tool components can provide discovery, script conversion, result
analysis, calibration support, data export, or other non-step services. They use
the same package, descriptor, schema, invocation, and isolation infrastructure.

Tool components do not receive implicit access to ARTestStudio UI. If UI support
is needed, the tool publishes schemas and declarative presentation metadata.
ARTestStudio renders trusted built-in controls around those definitions.

## Package manifest projection

The common manifest differentiates runtime activation while retaining identical
component descriptors.

Native:

```json
{
  "runtime": {
    "kind": "native",
    "entry": "ARTestDrvSimPower.dll",
    "abi": { "major": 0, "minor": 1 },
    "architecture": "x64"
  }
}
```

Python:

```json
{
  "runtime": {
    "kind": "python",
    "entry": "example_package.extension:create_extension",
    "protocol": { "major": 1, "minor": 0 },
    "python": ">=3.12,<3.14"
  }
}
```

.NET:

```json
{
  "runtime": {
    "kind": "dotnet",
    "entry": "Example.Extension.dll",
    "entryPoint": "Example.Extension.EntryPoint",
    "protocol": { "major": 1, "minor": 0 },
    "targetFramework": "net10.0"
  }
}
```

These examples express future capability; D1 supports only `native`. Unsupported
runtime kinds are cataloged as incompatible instead of being silently ignored.

## Failure and recovery behavior

| Failure | Engine behavior |
|---|---|
| Startup timeout | Mark endpoint unavailable; do not create components |
| Manifest/descriptor mismatch | Reject the complete package |
| Protocol mismatch | Mark incompatible and report supported range |
| Invalid payload | Fail the invocation; retain endpoint if protocol remains valid |
| Unhandled language exception | Record extension failure; apply step failure policy |
| Broken pipe/process exit | Invalidate all endpoint handles; fail active invocations |
| Cancellation ignored | Terminate after grace period; mark endpoint unhealthy |
| Driver cleanup failure | Preserve diagnostic and override successful run verdict |
| Repeated crash | Disable automatic restart for the run and require operator action |

Automatic endpoint restart never resumes an in-flight hardware operation. A
restart creates a new endpoint generation and requires explicit driver
reinitialization.

## Security baseline

- Package roots are explicit and canonicalized.
- Entry points cannot escape the package root through relative paths or links.
- No package installer runs during discovery or execution.
- Python dependencies are prepared separately from test execution.
- .NET probing paths are restricted to the package and approved shared runtime.
- Named pipes use current-user/process ACLs and unguessable session names.
- Manifests and runtime descriptors must match.
- Secrets are passed through scoped host services, not manifest files or command
  lines.
- Logs redact configured sensitive fields.

Package signatures, publisher trust, sandbox tokens, resource quotas, and remote
extension execution are later hardening work.

## D4 proof-of-concept acceptance criteria

1. One Python command and one .NET component are discovered from manifests.
2. ARTestCLI executes them without embedding CPython or CLR.
3. The same catalog representation is produced for native, Python, and .NET.
4. Parameters and results validate against the same schema system.
5. Cancellation and deadline propagation are demonstrated.
6. Exceptions become canonical diagnostics without crashing ARTestEngine.
7. Process termination invalidates handles and triggers guaranteed cleanup
   reporting.
8. No language-specific branch is added to parser, compiler, executor, or
   ARTestStudio parameter rendering.
